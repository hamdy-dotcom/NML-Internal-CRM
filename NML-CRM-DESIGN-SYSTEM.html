NML CRM — design system

Everything below is live HTML, not a picture. Screenshot any section at full width, or hand this file to Claude Code and it can read the real CSS.

How to use this with Claude Code. Copy the token block in section 2 into app/globals.css, copy the component classes from this file's <style> block as the starting point for your Tailwind theme, then build each screen against the rules in section 6. The screens here are static markup at desktop width — they show layout, hierarchy and state, not behaviour.

1. The idea in one paragraph

A gradient wallpaper sits behind everything. The entire application floats on it as one translucent, blurred pane. Panels nest inside that pane at lower opacity, and content cards sit inside those at higher opacity — so depth is expressed by how much white each layer holds, never by shadows or borders. Nothing has square corners. Nothing is grey-on-grey. Colour appears only where something has changed state or needs attention.

Type

  • Inter — all Latin UI. 11 / 11.5 / 12 / 13 / 14 / 16 / 22px. Two weights only: 400 and 500.
  • IBM Plex Sans Arabic — applied via :lang(ar) and on the public form. Arabic store names appear throughout the internal app, so this must load everywhere, not only on the form.
  • JetBrains Mono — merchant codes, phone numbers, SKU counts, prices, IBANs. Anything that gets read aloud, compared down a column, or pasted into another system.

Depth and blur

Only two elements carry backdrop-filter: the app window and any drawer or modal. Panels and rows inside them use flat rgba(255,255,255,x). Stacking real blur on fifty table rows costs GPU for no visual gain — the window behind them is already blurred.

4. Layout rules

  • Nav is role-filtered. An acquisition specialist sees four items and his home is called "My day". An admin sees all nine. Showing people locked doors every morning is friction with no upside.
  • Order on every list screen: search bar → stat tiles → panel containing tabs, filters, bulk bar, table. Never varies.
  • Filters collapse into one pill (Filters · 2) rather than a row of chips, so header height is constant across pages.
  • One primary action per screen, ink-filled, top right of the panel.
  • Everything is logical-property based (margin-inline-start, not margin-left) so the RTL flip on the public form costs nothing.

5. Writing rules

  • Sentence case everywhere. Never Title Case.
  • Buttons name their outcome and carry the count: Import 1,842 leads, not Submit.
  • Empty states name the next action: "The pool is empty. Import leads to get started."
  • Errors say what happened and what to do, in the interface's voice. Database rule violations surface verbatim — if the trigger says "assign an account manager first", that's the toast.
  • Row subtitles explain why something is in a queue — "form sent 4 days ago, no reply" — never just a date. A specialist with 142 merchants can't remember.

7. Still to design

These aren't drawn yet. They inherit the components above, so Claude Code can build them from the patterns — but they haven't been reviewed.

  • Modal family — log activity composer, change stage, mark lost, reassign, send form. All share the drawer shell in 6.3.
  • Form builder — settings screen for editing the merchant form's JSON schema without a deploy. The most complex remaining screen.
  • Reports — funnel drill-down, specialist performance, onboarding bottlenecks, shelf throughput. All use the funnel and table components from 6.8.
  • Settings — users and roles, teams, onboarding template editor, lookups.
  • Tasks — inherits the merchants table pattern.
  • Auth and system states — login, empty, loading skeletons, error, permission denied.
  • Account manager and catalog ops dashboards — same shell as 6.8 with different tiles.

8. Open decisions

  • Specialist capacity threshold — assumed 200 open merchants. Needs a real number; goes in settings as editable.
  • Product cost model — add nml_cost to the products table plus a per-merchant default margin agreed during onboarding, with per-product override.
  • Dedupe match order — Salla ID → store URL → phone. Confirm phone should count as a match at all; it's the loosest signal.
  • Onboarding template — the eight default steps drive every SLA and every colour on the onboarding board. They need to match how the team actually works.
  • Blocked steps — recommend requiring a reason, otherwise "blocked" becomes a parking space.
  • Brand assets — only #ED1C24 and white are exposed by nmlonline.sa. A real brand kit would replace the derived neutrals.
